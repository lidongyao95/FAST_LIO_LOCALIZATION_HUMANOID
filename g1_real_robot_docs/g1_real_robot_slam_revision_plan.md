# 《G1 真机 SLAM 部署指南》修改计划

审阅对象：`g1_real_robot_slam_notes.md`  
审阅日期：2026-11-03  
目标：将现有“仅用 x86 服务器的 SLAM 调试准备笔记”，改为面向初学者、由浅入深覆盖 **理解系统 → 接入真机传感器 → 建图 → 保存地图 → 重定位 → 导航适配 → 真机导航验收** 的完整指南。

本文件是修改计划，不是已经可执行的真机部署手册。此次仅阅读文档与仓库源码，没有连接机器人、启动驱动、发送运动命令或开展真机验收；原文保留不动。仓库之外的设备规格、网络能力和 SDK 行为，本次没有联网核验，以下列为后续核实事项。

## 一、总体判断

原文有价值的部分是：指出仿真脚本不能直接用于真机，发现驱动话题不一致、地图路径写死、保存地图方式等实际问题，并提出先录包、后离线调试的阶段流程。这些内容应保留。

但它不适合作为用户要求的完整入门指南，主要原因如下：

1. **目标偏窄。** 标题和主线围绕“仅用服务器”，正文主要讲网络与离线定位，导航仅占一个“后续”章节。读者无法从头走到完整导航链路。
2. **顺序倒置。** 在解释清楚 SLAM、定位、导航及其依赖关系之前，就给出设备 IP、编译和无线 AP 方案；读者只能照抄，难以理解为什么需要这些步骤。
3. **层次混杂。** 基础概念、当前仓库缺陷、环境特有路径、现场操作、Agent 分工和未来开发任务混在一起；已存在功能与计划开发功能没有统一标记。
4. **推断过强。** 若干观察被直接写成结论，例如“频率波动大说明无线丢包”“加速度 z 为负说明驱动错误”；缺少其他原因与适用前提。
5. **验收不完整。** 看到地图、话题有输出、服务返回成功，都不足以证明地图可用、定位正确或导航完成。各阶段缺少可记录的通过条件和失败后的返回位置。

重写应有两条相互配合的线：先用直观语言建立系统认识，再提供逐阶段操作卡；高级原理、源码证据和故障分析后置。

### 2.1 优先核查的技术问题

**A. 三类外参与倒装补偿必须分开讲。**

- 雷达点云坐标系与雷达内置 IMU 坐标系之间的外参。
- 雷达/IMU 与机器人机体之间的安装外参。
- 机体与导航地面投影坐标系之间的关系。

当前 `mid360.yaml` 含非零 `extrinsic_T`、单位 `extrinsic_R`，并启用 `extrinsic_est_en`；`main` 分支驱动又在 IMU 回调中旋转加速度与角速度。不能只根据“点云和 IMU 都转了 180°”就认定组合配置正确：应追踪点云输出路径、旋转方向、平移表达坐标和驱动 frame 名称，确认没有遗漏或重复补偿。这里只提出核查任务，不认定当前参数已经错误。

静止加速度检查应先说明输出坐标约定和单位。加速度模长、重力方向与实物姿态需要联合判断；`+1` 和 `+9.8` 不应在操作指南里作为不加区分的两种合法结果。

**B. 时间和数据质量不能仅看 `hz`。**

`ping` 证明的是 ICMP 可达性；话题频率证明的是观察端收到消息的节奏。二者均不能单独证明点云、IMU 完整且同步。应补充：驱动发布配置、包和帧时间戳、点内相对时间、时间回退与间隙、点数变化、录包丢失提示、CPU/磁盘负载、QoS 与有线对照。

“无线延迟不改变设备时间戳”也不等于算法不受影响；应检查驱动的实际时间来源、同步模式、到达顺序和缓冲行为。10 Hz、200 Hz、每帧约两万点、20～30 Mbps 均需标明所依据的设备/驱动设置或测量，不作为固定合格线。

**C. 导航坐标链不能只靠替换高度修好。**

原文建议将仿真 `foot_height` 换成雷达到地面的高度，这不足以构成实机 TF 方案。当前 `g1_nav_tf.py` 对输入位姿做平面化和高度处理，保留仿真机体语义；真机应先确定输入实际代表哪个 IMU/机体原点，再处理完整安装变换、地面基准、姿态与双足步行起伏。

重写时应给出目标坐标链及唯一发布者表，例如：

```text
map → odom → base_footprint → base_link → lidar / lidar_imu
```

这是待适配设计示意，不能直接宣称当前 launch 已提供该链。必须核对现有 `camera_init`、`body`、`imu_link` 和 `/Odometry` 的实际含义，避免一个子坐标系有多个父坐标系或重复 TF 发布。

**D. 二维地图生成脚本包含必须解释的假设。**

`export_g1_map.py` 不只做高度投影：它用 z 的第 5 百分位估计地面，对地面覆盖区域膨胀，并默认将原点附近 `known_free_radius=1.5` m 的区域标为已知空闲（障碍格仍优先）。这些处理可能把未观测区域当作可通行区域，原文没有交代。

应在教程中解释 free/occupied/unknown、地图原点与分辨率、三维/二维地图坐标一致性；初次验证建议关闭原点空闲补全（`--known-free-radius 0`），检查生成结果，再决定是否启用。该脚本仅支持未压缩 binary PCD，也应写出输入要求。

**E. 地图保存服务返回值不能当作文件验收。**

当前 `map_save_callback()` 在启用保存时调用 `save_to_pcd()` 后直接设置成功。文档应要求确认文件存在并可读回，而不是仅凭服务消息结束验收；后续若修改实现，再考虑传播底层写入错误。

**F. 运控和 ROS 域隔离需要区分。**

`walking_env.sh` 使用 `${ROS_DOMAIN_ID:-72}`，会保留已有的域值，不能写成“source 后一定是 72”。SDK 的 DDS 通信还应单独检查实际域和网卡选择；`ROS_LOCALHOST_ONLY=1` 不能作为全部机器人通信已隔离的证明。

`LocoClient` 方法、指令持续时间、断链行为、遥控接管和停止语义，应核对现场固件、SDK 固定版本与官方资料。不能把 `StopMove()` 软件停止直接等同于硬件急停，也不能只在服务器写 watchdog 就宣称覆盖了断网停止。

## 三、新文档的建议结构与学习顺序

建议主文保持一条完整阅读线，不要求初学者先跳到仿真文档或源码找定义。每章先给读者问题，再解释原理，最后进入操作。

### 第 1 章：最终要实现什么

- 描述三个独立成果：遥控采集并建图、加载既有地图定位、指定目标后自主行走。
- 用一张图说明数据链路与控制链路。
- 说明仓库目前提供哪些实现、哪些只有仿真验证、哪些仍需开发与真机验证。
- 给出全流程进度表，防止读者把“能看点云”误认为“SLAM 已完成”。

### 第 2 章：够用的基础概念

按依赖顺序解释：点云与 IMU → 里程计 → 建图与漂移 → 已知地图定位 → 路径规划与局部避障 → 速度指令与底层运控。

必须回答：

- FAST-LIO 输出什么？为什么有里程计还需要地图定位？
- 本仓库是否包含回环与全局优化？源码核实后写清，不能把走回起点自然理解为完成回环校正。
- 三维点云地图和二维导航地图为什么同时存在？
- `/initialpose` 与导航目标分别表示什么？
- ROS 话题、服务、Action、TF、QoS、`/clock` 各解决什么问题？

用一个“机器人从门口出发，建图后重新启动并走到桌旁”的例子贯穿全文。

### 第 3 章：认识自己的 G1 与部署方案

先填写设备清单：型号/EDU 与否、PC2 是否可用、雷达型号与安装、系统/架构、固件、可用运控接口、物理网口与供电。IP 表使用“示例值/现场确认值”两列。

比较三种路径：

| 方案 | 主要用途 | 必须说明的条件 |
|---|---|---|
| 外部 x86 有线采集/处理 | 初始连通、数据质量基线与离线调试 | 网线管理与移动范围 |
| 外部 x86 无线采集/处理 | 复用现有服务器开展实验 | 二层/路由与 UDP 接收能力、实测数据完整性、控制断链行为 |
| PC2 接收并运行算法，外部机器查看结果 | 机载运行候选方案 | 设备权限、架构/依赖、算力、散热和跨主机 ROS 通信 |

服务器方案可作为当前硬件条件下的一条完整操作路线，但不再作为所有 G1 的通用前提。具体推荐在确认设备条件后给出。

### 第 4 章：建立可复现的软件环境

- 列出 ROS/系统/架构、仓库提交、驱动来源及 SDK/Open3D 版本。
- 将仿真依赖与真机必要依赖分开解释。
- 先讲 workspace、build/install/source 和 overlay，再给命令。
- 独立驱动工作区的创建、构建、包查找验证；固定驱动提交，避免只写可变化的 `main`。
- 每个终端核验 ROS 域、RMW、实际加载的包路径与消息类型。
- 源码配置、安装配置、命令行覆盖各自在哪里生效。

### 第 5 章：接入雷达并验证数据

按“有线基线 → 正确驱动输出 → 坐标/单位 → 时间 → 录制 → 可选无线迁移”推进。

给出真实话题表：发布者、订阅者、类型、frame、频率来源、QoS。将驱动 UDP 网络和 ROS DDS 网络分别画出，避免把雷达可达与 ROS 节点可发现混为一谈。

输出成果：一段静止数据和一段短运动数据，以及采集配置与质量报告。

### 第 6 章：完成第一张三维地图

- 解释静止初始化、行走路线、视野覆盖与退化场景。
- A 段录制、停止、完整性检查；离线 FAST-LIO、回放时钟和 RViz。
- 保存 PCD，独立读回；解释地图坐标原点。
- 检查重复墙面、重影、地面倾斜、闭合路线接缝和不合理尺度。
- 给出实时建图分支：输入从 rosbag 换成驱动、关闭回放时钟，并避免两个输入源同时发布。
- 说明“不具备全局优化时，一次走完场景仍可能有累计误差”。

输出成果：地图文件、配置、采集包与质量记录。

### 第 7 章：加载地图并稳定定位

- 解释 FAST-LIO 局部里程计和点云地图配准如何协作。
- 使用独立 B 段验证；先测试已知起点，再测试不同起点、朝向和遮挡条件。
- 明确初始位姿的参考 frame、角度单位和适用范围；说明 RViz 二维初始位姿对三维姿态的限制。
- 检查时钟、TF、地图叠合、配准得分、时延与定位跳变。
- 从离线切换到实时，补充定位丢失后的停用导航、重定位和恢复过程。

同一段数据可用于回归和排查实现问题，但不能替代独立数据验收；原文“没有参考意义”的说法应改掉。

### 第 8 章：让定位结果满足导航接口

- 定义并验证 TF 树、`/odom`、机体速度和三维地图到二维地图的对应关系。
- 解释位姿修正为何应放在 `map → odom`，以及局部控制需要连续里程计。
- 导出并检查栅格；处理地面、低矮障碍、桌面、机器人自身点云和未知区域。
- 确定实时障碍输入；不能只把 CustomMsg 换为某个 PointCloud2 就宣布适配完成。
- 对照实际传感器原点、时间戳和滤波方式检查障碍标记及清除。
- 明确选择地图配准定位时，AMCL 的角色与 TF 发布权，避免重复发布 `map → odom`。

### 第 9 章：把 Nav2 速度接到 G1 官方运控

这一章明确分成“接口原理”“待实现清单”“验证后操作步骤”，开发完成前不伪造可运行入口。

- 解释 Nav2 负责规划与速度输出，G1 运控负责步态、平衡与执行。
- 记录 SDK/固件支持条件、控制模式、网卡、域、单位与返回状态。
- 定义速度桥输入、导航使能、限速/加速度、超时、停止和遥控接管状态机。
- 分别验证无目标、过期指令、取消目标、定位异常、进程退出与断链行为。
- 先独立验证桥，再接 Nav2；发布 ROS 零速度不等于证明真机已经停止。

### 第 10 章：完整导航部署与验收

- 创建真机独立参数与 launch，逐项关闭仿真时钟、移除仿真进程依赖。
- 联动检查 controller、velocity smoother、速度桥和实际运控约束。
- 用实际机体与步行范围确定 footprint、膨胀、障碍高度与恢复行为。
- 按“定位检查 → 地图与代价地图检查 → 只看规划 → 使能控制 → 短距离目标 → 多次重复”递进。
- 记录目标、轨迹、状态、实际终点、停止结果和相关 bag；区分 Action 成功与实际到达。
- 明确适用场景边界：本教程初期不将二维导航结果扩展为楼梯、多楼层或负障碍通行能力。

### 第 11 章：排错、恢复和日常运行

以现象为入口：无点云、无 IMU、没有地图、点云重影、定位跳变、TF 超时、机器人超出地图、能规划但不走、障碍不清除、停止未生效。

每项给“先停止哪个阶段 → 采集什么证据 → 按什么顺序定位 → 修复后从哪一步重新验收”。启动清单和关闭清单单独列出，支持以后日常使用。

附录放置：术语表、文件索引、仿真迁移对照、PC2 构建差异、服务器无线 AP 配置、Agent 与现场人员分工、源码证据和官方参考资料。

## 四、统一写法与操作卡模板

每个操作阶段按同一格式编写：

1. **本步目的：** 用两三句话解释为什么做。
2. **前置条件：** 明确上一阶段产物、当前机器和机器人状态。
3. **本步输入与输出：** 数据、配置、文件和话题。
4. **操作：** 分终端标号，标明 source、运行目录与必要变量；避免依赖隐藏 shell 状态。
5. **预期观察：** 展示正常输出含义，标明示例值不等于硬阈值。
6. **通过条件：** 有哪些证据才能进入下一步。
7. **失败处理：** 停止/保留什么、查看哪些日志、回到哪一步。
8. **退出与重做：** 正常关闭顺序、地图保存时点、重复执行及输出目录处理。

行文要求：

- 术语首次出现先用直观解释，再给正式名称；正文以任务为线索。
- 一条命令配一段必要解释，不连续堆砌无法理解的命令。
- 使用“仓库源码已核对 / 离线已验证 / 真机待验证 / 待开发”状态标记。
- 不将历史仿真验收、静态代码存在、进程启动、RViz 显示当作真机效果证据。

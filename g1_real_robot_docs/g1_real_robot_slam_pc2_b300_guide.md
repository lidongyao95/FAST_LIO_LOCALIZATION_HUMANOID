### 0.1 算力：以 PC2 单机为主

当前按第 0 节的实机配置部署。PC2 已跑通静止感知链路，定位、Nav2 和持续负载按后续阶段验证。

- **不再把服务器作为默认方案。** 把一楼服务器搬上来、拉网线、维护两套环境都很麻烦，先把驱动、FAST-LIO、定位和 Nav2 全部放在 PC2 上跑。
- **估计 PC2 够用**，但这是估计，不是实测结论。第 4.1 节先核实 PC2 的系统与架构，第 6.6 节和第 11 章用实际负载、时延和地图质量判断是否真的够用。
- **备选一：把一楼服务器搬到楼上，用网线直连。** 只有 PC2 性能或依赖确实不满足时才启用，且仍走有线，不回到无线。
- **备选二：Ubuntu 4060 笔记本。** 可以当可视化/SSH 终端，也可以临时承担算力；4060 的 GPU 对这条以 CPU 为主的链路帮助有限，用它跑算法前先实测 CPU 负载、散热和续航。
- **单机运行的好处**是雷达 UDP、ROS 2 通信和算法都留在同一台机器上，不需要跨主机 DDS、无线覆盖和数据完整性排查。**代价**是 PC2 的算力、散热和磁盘成为唯一瓶颈，且可视化要看 PC2 的输出方式（本机屏幕、远程桌面或笔记本跨主机 RViz）。
- **外部电脑负责日常控制。** 启动/停止节点、看日志、改参数和看 RViz 都要通过外部电脑接入 PC2；Mac/Windows 用 SSH 或远程桌面，Ubuntu 笔记本可以跨主机跑 RViz，也可以直接跑本项目。具体差别见第 3.6 节。

后文的主线因此改为 PC2：第 3 章确定硬件，第 4 章在 PC2 上建环境，第 5～10 章全部在 PC2 上执行。服务器与笔记本的差异集中放在附录 B。

### 0.2 停止方式、现场保护与人员分工

每次自主行走或停止测试前，按该机型、固件的厂家操作规程确定人员数量、站位和保护装置，由现场负责人确认。本文不认定一人或两人徒手抓扶足以承受跌倒，也不认定所有停止方式都会使机器人失去支撑。原稿提出的扶持安排需纳入现场方案核实，不能代替经确认的保护措施。

- 现场保护人员按已确认方案操作，避开跌倒、夹挤和关节运动区域，不抓线缆；扶持位置和可承重部件须以厂家要求为准。
- 固定停止负责人和遥控接管人，明确各自触发条件、操作手段及通信方式；记录该设备实际可用的停止手段，不假设存在某个硬件按钮。

- 这条要求适用于第 9 章的停止验证和第 10 章的完整导航演示，不因为“只是短距离”而省略。

### 0.3 场景：在 B300 门口演示，提前建好那里的图

按原稿安排，演示位置选在 **B300 门口**；现场负责人需按第 0 章补齐确认记录。建图范围按该场景准备。

- **必须提前建图。** 现场直接扫图很容易失败，失败就得重扫，而演示现场不具备重扫的时间和空间条件。正确顺序是：提前在 B300 门口完成建图、保存地图、验证重定位，演示当天只加载已保存的地图。
- **建图条件要和演示条件一致。** 建图时就把窗帘拉上、灯打开，记录门是开是关、桌椅和纸箱的位置、走廊是否有人走动。演示当天复现同样的窗帘、门和家具状态，否则点云结构变化会影响定位。
- **窗帘状态保持一致。** 本项目拟采用拉上窗帘的场景；实际回波受玻璃、窗帘材质、摆动和几何影响，不能保证遮住室外结构或消除噪声。先检查原始点云中的玻璃残余回波、窗帘回波与稳定性，再决定并记录状态。
- **灯要打开。** 保持照明稳定，便于现场人员观察、录像和判断机器人状态；如果同时使用相机，也能避免明暗突变。建图和演示使用同一组灯。
- **提前彩排。** 至少在演示前完整走一遍“加载地图 → 初始化 → 给目标 → 到达”，确认地图覆盖门口到目标点、初始朝向可用、现场人员明确保护与停止分工。

## 1. 最终要完成的三件事

设想 B300 门口：G1 从门口出发，遥控走遍门口和走廊这一段，随后关掉 SLAM 程序。下一次启动（也就是演示当天）时，它能够确定自己在门口的位置；你在地图上点击走廊里的一点，它可以规划路线、避开障碍并走过去。

这个目标要分成三个独立成果。

### 1.1 建图、定位、导航

**建图：先认识环境。** 雷达测量周围物体，IMU 测量角速度和加速度。算法估计运动，将不同时刻看到的点云放到同一个坐标系中，得到环境地图。

**定位：在已知环境中确定自己在哪里。** 重新启动后，算法将当前扫描和保存的地图配准，估计机器人相对地图的位置和方向。建图时走得好，不代表重启后一定能定位成功。

**导航：根据位置和环境决定怎么走。** 导航系统接收目标，生成路线，根据附近障碍调整运动，向运控发速度。宇树运控负责将速度要求变成步态与关节动作。

因此可以先用遥控器完成建图和定位实验，不必先训练行走策略。只有自主导航阶段才需要把导航速度连接到真机运控。

### 1.2 两条链路

```text
传感器与地图链路
MID-360 → Livox 驱动 → 点云 + IMU → FAST-LIO → 局部里程计、扫描、三维地图
                                                   │
保存的三维地图 ──────────────────────→ open3d_loc → 地图中的定位
保存的三维地图 → 二维投影 → 栅格地图 ─────────────────────┐
实时障碍点云 + 定位 + 里程计 ────────────────────────────┤
                                                       ▼
运动控制链路                              目标 → Nav2 → 速度桥 → 宇树运控 → 行走
```

建图阶段主要运行上面的数据链路。导航阶段才闭合到实际运动。排错时也沿这两条链路逐段检查。

## 2. 先理解够用的基础概念

### 2.1 点云、IMU 和里程计

点云是一批三维坐标，例如墙上、地面和桌面的测量点。一帧点云不是一张有颜色的照片；它记录的是传感器看到的空间结构。

IMU 提供角速度和加速度。机器人运动时，一帧点云中的点通常并非完全同时采集，IMU 有助于估计扫描期间的运动并补偿畸变。点云时间和 IMU 时间对不上，地图可能出现弯曲、重复墙面或漂移。

里程计回答“从本次启动以来移动了多少”。FAST-LIO 融合点云与 IMU，在局部坐标系中持续估计运动。由于测量和建模误差，这种估计可能逐渐漂移。

### 2.2 FAST-LIO 和地图定位各做什么

本仓库 FAST-LIO 的建图链路维护局部点云地图并估计里程计；本文使用的启动链路没有额外启动回环检测和位姿图全局优化模块。走回出发点不等于已经进行了回环校正，累计误差仍需检查。

`open3d_loc` 读取已有地图，将当前扫描配准到地图，计算局部里程计与地图之间的关系。这样，机器人既有连续的局部运动估计，又可以在保存的环境地图中定位。

这里的“重定位”通常需要合理的初始位置和朝向。不能因为名字中有 `global_localization`，就假设它一定能从任意位置、任意朝向自动识别全局位置。

### 2.3 为什么有三维地图和二维地图

三维点云地图用于保留空间结构，供点云配准定位使用，常保存为 PCD 或 PLY。

Nav2 的常见地面导航流程使用二维栅格地图。每个格子表示已知空闲、障碍或未知。它便于搜索平面路径，但不能完整表达桌面上下空间、台阶、楼梯和悬崖。因此本文初期目标限定为单层室内平地，不把二维导航能力外推到上下楼或负障碍通行。

**代价地图**是在栅格基础上供规划和控制使用的环境表示：既可以纳入静态地图，也可以加入实时障碍，并将障碍附近区域提高代价，让机器人保持距离。

### 2.4 ROS 2 中最常遇到的接口

| 名称 | 直观理解 | 本文例子 |
|---|---|---|
| 话题 topic | 持续发布的数据流 | 点云、IMU、里程计、速度 |
| 消息类型 | 数据格式 | CustomMsg、PointCloud2、Odometry、Twist |
| 服务 service | 一问一答的操作 | `/map_save` 保存地图 |
| Action | 可反馈、可取消的长任务 | 导航到某个目标 |
| TF | 不同坐标系之间的变换 | 地图、机体和雷达的位置关系 |
| QoS | 发布者与订阅者如何交付数据 | 可靠性、队列、历史数据保留 |
| `/clock` | 仿真或回放使用的时钟 | 支持该选项的 rosbag2 可用 `ros2 bag play --clock`；本机 Foxy 无此选项 |

消息格式必须匹配：CustomMsg 不是 PointCloud2，只改话题名字不会改变格式。QoS 也可能影响是否收到消息，遇到空话题时要同时看类型和 QoS。

### 2.5 坐标系、外参和初始位姿

坐标系包括原点和轴方向。雷达测得的点首先属于传感器坐标系；要把它放到地图里，就需要一串旋转和平移。

外参表示固定的安装关系，至少要分清三种：点云与雷达内置 IMU、雷达/IMU 与机器人机体、机体与导航地面投影。它们不能共用一个“雷达高度”代替。

初始位姿是告诉定位系统“现在大概在地图哪里”。导航目标是“接下来要去哪里”。RViz 中的 `2D Pose Estimate` 和导航目标工具承担这两个不同任务，使用时先确认实际发布的话题或 Action。

| Ubuntu 4060 笔记本 | 本机跑算法，或只做查看终端 | 备用算力/可视化终端 | 网卡与 UDP 接收、散热、跨主机 ROS |
| 外部服务器无线 | 服务器留在楼下，无线接收 | 不采用 | 数据完整性、覆盖、断链排查成本高 |

**本次选 PC2 的理由**是把问题收敛到一台机器：雷达 UDP、ROS 2 通信和算法都在本机，不需要跨主机 DDS、无线覆盖和数据完整性排查。代价是 PC2 的 CPU、内存、磁盘和散热成为唯一瓶颈，所以第 5 章的输入检查和第 6.6 节的实时建图必须真正测负载，不能只确认节点能启动。

**为什么不再先做无线基线。** 无线方案需要额外排查 AP/桥接、UDP 丢包、ROS QoS 和跨主机时钟，出问题时很难判断是算法还是链路。服务器搬上楼用网线，能保留有线方案的确定性；如果连搬服务器都嫌麻烦，那更不应该用无线去换活动范围。

### 3.3 备选一：把一楼服务器搬上来，用网线直连

只有 PC2 性能或依赖确实不满足时才走这条路线。原则是**搬机器、拉网线，不回到无线**。

1. 先确认 PC2 到底卡在哪里：是 CPU 满载、内存不足、磁盘写满，还是依赖装不上。不要因为一次建图慢就直接搬服务器。
2. 规划服务器位置：靠近机器人活动区域、有市电、通风、不会被踢到；网线沿墙或走线槽固定，跨通道处加线槽或胶带压平，避免绊人和被机器人压断。
3. 服务器加一块与雷达同网段的网卡，或在同一交换机上接雷达和服务器；接收地址改成该网卡地址（示例 `.222`）。**不要改服务器默认路由**，保留原来的上网和 SSH 路径。
4. 服务器仍是 x86_64 Ubuntu 22.04 时，可按[通用部署笔记](g1_real_robot_slam_notes.md)第 4 章准备 x86 工作区；执行机器从 PC2 换成服务器，地图和录包路径按服务器磁盘调整。
5. 服务器与 PC2 若同时在线，只能有一台接收雷达 UDP，避免两个驱动争用或互相改写雷达目标地址。

如果网线长度、走线条件或供电不允许，就不要勉强搬服务器，回到 PC2 或笔记本方案。

### 3.4 备选二：Ubuntu 4060 笔记本

笔记本有两种用法，不能混为一谈。

- **只做查看终端：** 在笔记本上装 ROS 2 Humble，在域、RMW、消息定义和跨发行版互操作性实测通过后订阅 PC2 的话题运行 RViz。此时笔记本不需要 Livox SDK 和雷达网段，但需要正确的 DDS 配置、防火墙放行和版本匹配。
- **临时承担算力：** 用有线网口或 USB/Type-C 网卡接入雷达网段，确认能收到 UDP 后再装驱动和算法。注意合盖休眠、电源管理和散热，长时间满载时插电并垫高。

RTX 4060 的 GPU 对 FAST-LIO 和 Open3D 配准帮助有限，这条链路主要吃 CPU 单核与内存带宽。不要假设“4060 一定比 PC2 快”，应实测帧率、延迟和积压。Ubuntu 版本要与 ROS 2 发行版匹配，避免在演示前临时升级系统。

### 3.5 两种网络不要混淆

```text
雷达 UDP 网络：MID-360 → 网络设备 → PC2 上的 Livox SDK/驱动
ROS 2 网络：驱动 → FAST-LIO → 定位 → RViz/Nav2（默认都在 PC2 本机）
运控通信：速度桥 → SDK → G1 运控服务
```

驱动直接接收雷达 UDP，不靠 ROS DDS 发现雷达。全部 ROS 节点在 PC2 时，不需要跨主机 ROS 数据传输；若 RViz 放在 4060 笔记本，则需要额外处理 DDS 通信和防火墙。

`ROS_LOCALHOST_ONLY=1` 只用于本机 ROS 场景，不能证明 Unitree SDK 或其他网络程序也被隔离；一旦笔记本要看话题，就不能再保持这个设置。运控 SDK 的网卡和域应单独配置。

### 3.6 用外部电脑（Mac/Windows/Ubuntu）完成基本控制

结论：可以，而且这是日常操作的主要入口。启动/停止节点、改参数、看日志、传文件和看 RViz 都要通过外部电脑接入 PC2 才能完成；不接入 PC2，基本无法开展调试和演示。需要图形界面时再开远程桌面。只有 Ubuntu 笔记本适合在本机直接跑 ROS 2 和本项目。

| 外部电脑 | 推荐接入方式 | 能做什么 | 限制 |
|---|---|---|---|
| Mac | SSH（终端自带）+ 远程桌面（NoMachine/VNC） | 启停节点、看日志、`scp`/`rsync`、通过远程桌面看 RViz | macOS 没有 ROS 2 Humble 的官方二进制安装包，通常不在本机跑节点 |
| Windows | 内置 OpenSSH 或 PuTTY + 远程桌面（RDP/NoMachine/VNC） | 同上 | 本机装 ROS 2 可行，但本项目的 Livox SDK、Open3D、Unitree SDK 和脚本都是 Linux 路线；WSL2 能跑但网卡和 DDS 配置复杂 |
| Ubuntu 笔记本 | SSH；原生 ROS 2 Humble + 同域 DDS | 既可当终端，也可跨主机 RViz，甚至直接跑本项目 | 需匹配依赖和架构；接雷达时只能有一个接收端；控制真机时确认 Unitree SDK 网络可达 |

这里的“控制”指启动/停止节点、修改参数、查看话题和日志、传地图和录包、看 RViz，不包括远程操纵机器人行走。停止操作、遥控接管和现场保护必须由现场人员落实。

**SSH 是首选。** Mac/Linux 直接 `ssh <user>@<PC2_IP>`；Windows 用自带 OpenSSH 或 PuTTY。建议在 PC2 上用 tmux 保持采集和建图进程，SSH 断开不影响运行；但运动控制的停止机制不能只依赖 SSH 会话，仍按第 9 章单独验证。

**远程桌面只用于看界面。** Mac/Windows 安装 NoMachine/VNC/RDP 客户端，PC2 装服务端。远程画面里的 RViz 卡顿不等于算法实时性差；不要用远程桌面判断帧率和延迟，实时性以 PC2 本机的日志和话题频率为准。

**Ubuntu 笔记本可以更深入。** 装好 ROS 2 Humble 后，它可以：

- 跨主机运行 RViz：设置与 PC2 相同的 `ROS_DOMAIN_ID` 和兼容 RMW，PC2 关闭 `ROS_LOCALHOST_ONLY`，放行防火墙，确认 `ros2 topic list` 能看到 PC2 的话题。
- 直接跑本项目：按第 4 章在笔记本上装依赖、构建；接雷达时要改接收 IP，并保证 PC2 或其他机器没有同时接收 UDP；如果笔记本还要发运动命令，先确认 Unitree SDK 网络可达，并让 PC2 停止控制，避免两台机器同时发指令。

**Mac/Windows 远程连接服务器。** 如果 PC2 不够用、改用搬上楼的服务器，Mac/Windows 同样通过 SSH 或远程桌面连服务器，服务器再接机器人网络。此时 PC2 不再运行驱动和算法；远程连接只负责操作和查看，不要把机器人网络直接暴露到公网。

```text
Mac / Windows ──SSH / 远程桌面──┐
                                ├── PC2（默认控制主机）
Ubuntu 笔记本 ──SSH / ROS 2────┘
        └── 可选：Ubuntu 直接跑本项目（此时 PC2 不重复运行）

Mac / Windows ──SSH / 远程桌面──→ 服务器（备选算力）→ 机器人网络
```

**任何时候只允许一台机器作为控制主机。** 默认是 PC2；只有明确切换时才改服务器或 Ubuntu 笔记本。多台电脑同时启动驱动、Nav2 或速度桥，会出现两个接收端、重复 TF 或两路速度命令。外部电脑默认只做节点操作和观察，不直接发布运动指令；停止操作和现场保护仍由现场人员落实，远程连接断开不能作为唯一的停止手段。

### 4.2 在 PC2 上准备现有工作区

当前 PC2 已构建，可直接做包检查。需要重建时，先确认 PC2 部署副本保留第 4.4 节的两处驱动配置、系统依赖和本机编译的 Livox-SDK2 1.3.1，再从干净的 Bash 执行：

### 4.3 固定并记录版本与资源

PC2 上是 rsync 部署副本。同步时从开发机记录 Git HEAD、未提交改动、依赖版本及驱动配置差异，在 PC2 保存 `uname -m`、`cat /etc/os-release`、`/usr/bin/python3 --version`、`df -h` 和构建日志。本次复核盘上剩余约 1.8 TiB。

### 4.4 选择驱动，先明确坐标约定

实机使用 `$G1_REPO/.deps/src/livox_ros_driver2`，由同一工作区安装。安装副本已核对：

- `config/MID360_config.json` 中雷达地址为 `192.168.123.120`，五个 `host_net_info` 接收地址均为 PC2 的 `192.168.123.164`，JSON 外参为零。
- `launch_ROS2/msg_MID360_launch.py` 使用 `xfer_format=1`、`frame_id='livox_frame'`，把点云以 `livox_ros_driver2/msg/CustomMsg` 发到 **`/livox/lidar`**。该 launch **没有**做话题重映射，因此不存在 `/livox/custom_msg`；若工作区其他配置仍按该名订阅，要么改用 `/livox/lidar`，要么在 launch 的 `Node(...)` 中加 `remappings=[('/livox/lidar', '/livox/custom_msg')]`。配置含义见 [Livox 官方驱动说明](https://github.com/Livox-SDK/livox_ros_driver2)。2026-11-05 在第二台 G1 上实测确认，见[静止基线采集](debug_log/2026-11-05_pc2_build_pitfalls.md#4-静止基线采集)。

同步代码前保存这两处 PC2 改动。更改驱动源码配置后重新构建并检查安装副本。历史驱动中的 180° 补偿属于另一版本。当前零外参仅描述驱动配置，雷达实际安装方向、FAST-LIO 外参与导航机体变换仍需现场核对。

## 5. 接入雷达，确认输入可以用于算法

### 5.1 网络与端口

**前置条件：** 现场已确认雷达型号、IP、PC2 网卡和接收配置；机器人保持可控状态。本次雷达通过机身网络接到 PC2，属于有线连接，先完成静止检查。

```bash
ip -br addr
ip route get 192.168.123.120
ping -c 20 192.168.123.120
ss -ulpn
```

这些是本机实测地址。安装 JSON 使用 56101、56201、56301、56401、56501；只搜索 `563` 会漏掉 IMU 和控制端口。还要检查 PC2 或其他主机是否已有接收程序，以及它们是否会重新配置雷达的目标地址。

`ping` 成功只说明 ICMP 可达，不说明雷达 UDP 已到达正确端口。收不到数据时检查目的 IP、路由、端口占用、防火墙和驱动日志；需要时在指定网卡抓包观察，不先重装算法。

### 5.2 启动一个驱动并检查消息

终端 D：加载第 4.2、4.4 节运行环境，启动：

```bash
ros2 launch "$G1_REPO/install/livox_ros_driver2/share/livox_ros_driver2/launch_ROS2/msg_MID360_launch.py"
```

终端 Q：使用相同运行环境检查：

```bash
ros2 topic list -t
ros2 topic info /livox/lidar --verbose
ros2 topic info /livox/imu --verbose
```

本机 Foxy 的 `ros2 topic hz` 曾超时无输出。以短包的 `ros2 bag info` 计数和时长作为复核依据，`static_01` 已记录点云 115 条和 IMU 2306 条。消息头的连续性与主机对时分开验收，见 [静止录包复核](debug_log/2026-11-04_g1_pc2_slam.md)。

### 5.3 话题与坐标对照表

以下为当前源码接口；驱动重映射按第 4.4 节完成后生效。运行时仍应检查真实 header 和 QoS。

| 话题 | 类型 | 发布者 → 使用者 | 坐标/用途 |
|---|---|---|---|
| `/livox/lidar` | `livox_ros_driver2/msg/CustomMsg` | 驱动 → FAST-LIO | 候选驱动配置为 `livox_frame`，输出坐标需核查 |
| `/livox/imu` | `sensor_msgs/msg/Imu` | 驱动 → FAST-LIO | 真机为雷达内置 IMU，不是仿真骨盆 IMU |
| `/Odometry_loc` | `nav_msgs/msg/Odometry` | FAST-LIO → 定位/适配器 | `camera_init` 下的 `body` 位姿 |
| `/cloud_registered_1` | `sensor_msgs/msg/PointCloud2` | FAST-LIO → 定位 | `camera_init` 下的扫描 |
| `/cloud_registered_body_1` | `sensor_msgs/msg/PointCloud2` | FAST-LIO → 可选障碍处理 | `body` 下的扫描 |
| `/localization_3d` | `geometry_msgs/msg/PoseStamped` | 定位 → 监控 | `map` 下的输出位姿，具体机体点由变换决定 |
| `/localization_3d_confidence` | `std_msgs/msg/Float32` | 定位 → 监控/门禁 | 配准 fitness 指标 |
| `/map` | `sensor_msgs/msg/PointCloud2` | 旧定位入口 → RViz | 与导航栅格地图同名，导航适配时必须重映射 |

### 5.4 检查坐标、单位与时间

```bash
ros2 topic echo /livox/imu --once
ros2 topic echo /livox/lidar --field header --once
ros2 topic echo /livox/lidar --field point_num --once
```

这些命令只用于抽查；连续性需要对一段录包做统计。

- **静止：** 加速度模长和方向应符合所选坐标和驱动单位；角速度应接近静止噪声水平。先核查驱动是否将原始值直接填入 ROS 消息，不把 `1 g` 和 `9.8 m/s²` 当作可以不加说明地互换。
- **方向：** 对照实物轴向，检查点云中地面、墙体和受控姿态变化。仅看加速度 z 的正负不足以判定倒装补偿正确。
- **外参：** 核对点云—IMU、传感器—机体的旋转和平移。`mid360.yaml` 中 `extrinsic_T=[-0.011,-0.02329,0.04412]` 和单位旋转是现有参数，不是本机已完成标定的证明；在线外参估计也不能替代安装语义核查。
- **时间：** 检查点云帧时间、CustomMsg 点内时间和 IMU 时间是否连续、同基准；关注回退、大间隔、覆盖范围不匹配和驱动同步模式。
- **数据完整性：** 联合检查点数变化、帧间隔、驱动错误、录包提示和 PC2 负载；先把同一台机器上的负载、温度和驱动日志记录下来，再判断是否需要换机器或换链路。

`mid360.yaml` 的 `time_sync_en=false`、时间偏移 0 只表达当前设置，不证明传感器已经同步。不要遇到漂移就随意启用软件时间补偿。

正式录制前执行 `timedatectl`、`chronyc tracking`、`chronyc sources`，记录同步状态与偏差。PC2 曾慢约 680 秒，换电重启后恢复同步。每次正式采集前复查主机状态，再核对传感器时间基准、帧内逐点时间和动态对齐。见 [换电前后对时记录](debug_log/2026-11-04_g1_pc2_slam.md)。

### 5.5 先录两段短数据，再开始正式采集

已有 `$G1_DATA/bags/static_01`。复录时使用新目录名。先确认 `$G1_DATA` 所在分区有空余空间（`df -h`），并观察 PC2 的温度和风扇。录包要写 PC2 本地磁盘，不要写到网络共享或慢速 U 盘；磁盘写满或写入阻塞，首先表现为丢帧和时延，而不是明显的报错。

终端 R 使用相同 overlay：

```bash
ros2 bag record -o "$G1_DATA/bags/static_02" /livox/lidar /livox/imu
```

现场保持静止，记录一段足够观察时间连续性的数据后 Ctrl-C，等待录制器退出，再检查：

```bash
ros2 bag info "$G1_DATA/bags/static_02"
```

随后用新目录录一次短距离遥控运动，包含直行、缓慢转向和停止。若 recorder 与发布者 QoS 不兼容，先根据 `topic info --verbose` 制定录包 QoS 覆盖文件，并确认实际录入消息，不能只看录制进程存在。

**本章通过条件：** 输入类型、坐标、单位和时间有记录，两路消息都被保存，静止与运动数据不存在尚未解释的异常。失败时保留包和驱动日志，回查网络、坐标或时间，再重复短数据检查。

## 6. 用真实数据完成第一张三维地图

### 6.1 准备演示场景、路线和配置

**目的：** 按项目安排在 B300 门口演示，建图必须提前完成。现场直接扫图容易失败，失败后重扫既费时间，也很难复现同样的光照和遮挡，所以先把场景条件固定，再准备路线和配置。离线建图还能把算法调试与现场行走分开，减少现场试错。

建图范围至少覆盖：B300 门口、门口外的走廊段，以及演示时机器人从起点到目标点要走的路线。不要只扫门内或只扫走廊，定位和导航都需要门口附近的共同结构。

开扫前逐项完成并记录：

1. 按第 0.3 节检查并记录窗帘与玻璃实际回波，确定窗帘状态；打开灯用于观察、录像及可选相机。建图和演示复现同一状态，不把灯光或窗帘状态本身当作 LiDAR 定位有效的证明。
2. 记录门是开着还是关着；演示时会关门，建图时也要关门。门是点云里很强的特征，开关状态变化会影响重定位。
3. 移走或固定走廊里的纸箱、推车、椅子和临时杂物；不能移走的家具记录位置。
4. 清空路线上的线缆、水渍和门槛处的松动物品；安排人员避开雷达视野，不要长时间站在机器人正前方。
5. 记录建图日期、时间段、灯光状态、窗帘状态、门状态和在场人员，作为演示前复现条件的依据。

**前置条件：** 第 5 章输入检查通过；上面的场景条件已记录；机器人仍由现场人员使用宇树运控遥控行走。路线就是 B300 门口到走廊这一段，缓慢转向，避免长时间只看无结构墙面或被人体遮挡。

复制候选配置，保留仓库默认值：

```bash
cp "$G1_REPO/FAST_LIO/config/mid360.yaml" "$G1_DATA/config/mid360_real.yaml"
```

在该副本中记录已核对的输入话题、外参、时间设置和过滤参数。它应为 `lidar_type: 1` 的 CustomMsg 路线。不要改用仿真 `g1_*.yaml` 中的模拟雷达类型和 0.45 m 安装高度。

### 6.2 录制建图 A 段

保持驱动运行，终端 R 启动：

```bash
ros2 bag record -o "$G1_DATA/bags/map_A_01" /livox/lidar /livox/imu
```

开始时在 B300 门口、演示时的初始朝向静止约 10 秒作为首次采集建议，确认输入正常再遥控行走；初始化是否完成仍以算法状态和数据为准，不以固定等待秒数判断。走遍需要覆盖的区域，尽量让相邻路段有共同可见结构，并回到可辨认的位置。遥控行走时安排一人跟在机体侧后方，避免撞到门框、墙角和走廊里的杂物。

结束时停稳，Ctrl-C 停止录制，等待退出，用 `ros2 bag info` 核对时长、类型和两路消息数量。再停止驱动，准备离线回放。不要让驱动与回放同时向相同输入话题发数据。

另用新目录采集 B 段验证数据，先停止 A 录制再开始 B。B 首次可从相同起点和朝向出发，但路线应独立；后续增加不同起点与朝向。记录每段起点、朝向、窗帘/灯光/门状态和现场人员位置。

### 6.3 离线运行 FAST-LIO

以下三个终端都加载第 4 章运行环境。终端 M 先创建输出目录，再运行算法：

```bash
mkdir -p "$G1_DATA/maps" "$G1_DATA/records"
ros2 run fast_lio fastlio_mapping --ros-args \
  --params-file "$G1_DATA/config/mid360_real.yaml" \
  -p use_sim_time:=false \
  -p map_file_path:="$G1_DATA/maps/b300_door_01.pcd" \
  -p debug_log_dir:="$G1_DATA/records"
```

终端 V 运行 RViz：

```bash
rviz2 -d "$G1_REPO/FAST_LIO/rviz/fastlio.rviz" \
  --ros-args -p use_sim_time:=false
```

若 PC2 没有接显示器，先按附录 A 选择远程桌面或笔记本跨主机 RViz，再执行；不要在无显示环境下反复启动 `rviz2` 并把它当作程序故障。

建图时 Fixed Frame 使用 `camera_init`，检查显示订阅的是本节实际输出话题。终端 P 最后开始回放：

```bash
ros2 bag play "$G1_DATA/bags/map_A_01"
```

本机 Foxy 的播放器没有 `--clock`。此处使用原始消息头做 FAST-LIO 离线处理。历史 TF 用于可视化时，需单独验证 RViz 对历史时间戳的处理。首次以正常速度回放；若出现处理积压，先记录负载和延迟，再降低回放速度做离线对照，不能把慢速回放成功当作实时能力已满足。

### 6.4 保存并读回地图

回放结束后，**保持 FAST-LIO 运行**，在终端 Q 调用：

```bash
ros2 service call /map_save std_srvs/srv/Trigger '{}'
```

当前实现保存的是内存点云，`pcd_save_en` 必须开启，目标目录必须存在。不要依赖退出时自动生成 `scans.pcd`。

服务返回成功后，检查文件存在，并用导出脚本独立读取未压缩 binary PCD：

```bash
ls -lh "$G1_DATA/maps/b300_door_01.pcd"
/usr/bin/python3 "$G1_REPO/scripts/export_g1_map.py" \
  "$G1_DATA/maps/b300_door_01.pcd" --out "$G1_DATA/maps/b300_door_01" \
  --known-free-radius 0
```

该工具需要 Python `numpy` 和 `cv2`；现有 C++ Open3D 依赖不等于 Python Open3D 已安装。若导出缺少依赖，按环境依赖说明安装或使用可读 PCD 的独立点云工具，不能省略读回检查。

当前服务在调用写文件函数后直接设置成功，未将底层写入返回码用于服务结果，所以还应检查点数、有限坐标、范围和显示效果。二进制 PCD 不适合直接对全文件 grep 判定质量。

### 6.5 判断地图能不能进入定位阶段

在 RViz 或点云工具中检查：墙面是否重复、门框是否变形、地面是否倾斜、回到起点后是否出现接缝。选择几处可实际测量的距离比较尺度，并记录误差。阈值根据最终通行空间和定位需求制定，不在没有测量时宣称达到厘米级精度。

还要对照演示需求检查：B300 门口、走廊和目标点是否都在图内；门口的门框、墙角、消防栓或标识牌等特征是否清楚；如果演示时会关门，地图中门的状态要与演示一致。

**本章通过条件：** PCD 可独立读回，几何尺度合理，覆盖 B300 门口到目标点的区域，明显重影/漂移已解释或修复；保存配置、版本、原始 A 包、地图和场景条件记录。之后停止 FAST-LIO、RViz。

**失败恢复：** 不用错误地图继续调定位。先回查输入时间和外参，再看运动畸变、场景退化和算法处理能力。重跑时重启算法并用新输出名，避免将前次内存状态带入结果。

### 6.6 从离线换为实时建图，并确认 PC2 撑得住

停止播放器及离线 FAST-LIO，重新启动驱动。沿用核对过的配置启动新的 FAST-LIO，将 `use_sim_time` 改为 `false`，使用新的地图路径；RViz 也改为实时。

实时运行是判断 PC2 够不够用的关键一步，至少记录以下内容：

- 用 `top` 或 `htop` 观察各进程 CPU 占用，确认 FAST-LIO 是单核吃满还是整体过载。
- 记录输入频率，同时检查输入到算法输出的时间差、扫描/里程计年龄及处理队列；上游频率稳定或 RViz 流畅不能证明算法无积压。
- 使用设备可用的温度、CPU 频率与风扇接口记录数据；没有可读接口时标记“未测”，不能用出风口体感判断温度或降频。
- 记录内存随时间增长、磁盘写入和剩余空间；在受控条件下保存地图并检查是否影响输出时延。预先填写运行时长、采样间隔、重复次数及可接受阈值。

如果实时建图持续积压、降频或丢帧，不要等到演示当天再换机器，此时才启用附录 B 的服务器或笔记本方案。如果实时运行稳定，就继续用 PC2，并把本次负载记录写入验收记录。

实时数据比慢速回放更容易暴露积压，必须单独验收。

## 7. 加载地图，验证重定位与实时定位

第 7 章是定位适配参考。当前 PC2 缺少 `open3d_loc`，且 Foxy 的播放器不提供下文使用的 `--clock`。正式执行前须补齐依赖并验证所选定位栈的回放时钟方案。

### 7.1 先理解当前入口的坐标假设

**源码已核对：** `localization_3d_g1.launch.py` 包含 FAST-LIO、定位节点与 RViz；父入口声明并转发必填的 `path_map:=<PCD或PLY路径>`。子入口包含 `odom → camera_init`、`imu_link → base_link`、`base_link → motion_link` 的静态关系。它们不能未经检查就代表真机完整安装关系。

FAST-LIO 发布 `camera_init → body`；定位节点又读取命名为 `base_link`、`imu_link` 的变换。调试前必须在记录中说明 `body` 是否被当成雷达 IMU 原点、哪里转换为机体原点，以及零变换是否有实际依据。存在断开的 TF 或不一致的机体语义时，先完成适配，再评价定位精度。

旧 launch 静态发布 `base_link → motion_link`，定位节点又默认动态发布 `map → motion_link`，同时启用会使 `motion_link` 有两个父 frame。若采用旧机体链，诊断命令应显式设 `publish_motion_tf:=false`；这只能消除该项冲突，不能代替完整真机 TF 适配。

定位节点在构造阶段查询 `base_link ← imu_link` 和 `motion_link ← base_link`，查询失败返回 false，但调用方没有检查。必须先启动已测量的安装 TF、在检查终端确认可查询，再启动定位；若定位启动日志出现查询失败，补齐后重启定位，不依赖之后自动恢复。外部查询成功仍不能保证节点自己的 TF 缓存在构造期间已收到数据；源码增加等待 TF 和失败阻断前，这里仍是未验收的候选流程。

| 关系 | 本阶段候选发布者 / 状态 | 检查要求 |
|---|---|---|
| `map → odom` | 定位节点 | 初始化前也可能发布，不作为已定位证明 |
| `odom → camera_init` | 经核实的静态关系 | 仅在两坐标实际重合时可设单位变换 |
| `camera_init → body` | FAST-LIO | body 是 LIO 的 IMU 参考点，需核对驱动输出语义 |
| `body` 到机体安装链 | 真机适配方案待确定 | 必须连接内部与机体 frame，不可直接照搬零变换 |
| `imu_link → base_link → motion_link` | 仅在选用旧链且实测成立时由安装 TF 发布 | 记录轴向、原点和数值，不再由定位发布 `map → motion_link` |

上表列出当前诊断所涉及关系，完整可执行的真机 TF 链仍待实现，必须与第 8 章导航链统一发布权。下面显式启动命令仍以前述适配通过为前提。

### 7.2 设置定位参数

复制 `open3d_loc/config/loc_param_g1.yaml` 为：

```bash
cp "$G1_REPO/open3d_loc/config/loc_param_g1.yaml" \
   "$G1_DATA/config/loc_real.yaml"
```

配置中的 `initialpose` 为 `[x,y,z,roll,pitch,yaw]`，位置用米，该实现的欧拉角用**度**，且源码按 `Rx * Ry * Rz` 相乘，不能直接套用其他工具的欧拉角顺序。

源码将 `initialpose` 赋给初始 `map ← odom` 变换。在本次里程计起始接近单位变换时，才可近似把它理解为“机器人起点”。若局部里程计已运动，初始化变换应结合当前里程计求解。全零只适用于坐标和起点假设都成立的情况。

`/initialpose` 回调仅在 `!(loc_initialized_ && loc_fitness_ > 0.99)` 时更新该变换；已经初始化且 fitness 大于 0.99 时请求会被忽略。该回调未按消息 header 转换坐标，也没有使用 covariance 进行 AMCL 式初始化。二维工具不能表达任意三维初始姿态，不能无条件作为重置入口。

用 `T_A_B` 表示把 B 坐标变到 A 坐标，则应计算 `T_map_odom = T_map_base × inverse(T_odom_base)`。其中 `T_odom_base` 必须包含雷达 IMU 到机体的安装变换，不能直接拿传感器位姿代替。初值生效需结合回调更新日志、`map → odom` 数值及扫描叠合确认；高 fitness 时的强制重置接口尚待设计。

演示位置固定在 B300 门口，所以要把演示时的初始位置和朝向测出来并记录：在地面用胶带标出机身投影或两只脚的位置，以门框和走廊方向作为朝向基准，把对应的 `x`、`y`、`z`、`yaw` 写入 `loc_real.yaml`。标记点只能辅助复现摆放，不能直接确定传感器三维位姿；只有局部里程计和安装外参条件一致并确认配准正确时，才可复用初值。若机器人实际摆放偏离标记点，应按当前里程计重新求解，不要硬套记录值。

### 7.3 离线定位 B 段

先停止其他 FAST-LIO 和播放器。终端 L1 按第 6.3 节启动 FAST-LIO，仍使用 `use_sim_time=true`，不要同时再启动包含 FAST-LIO 的组合 launch。

终端 L2 运行定位节点。当前 `open3d_loc_g1.launch.py` 暴露 `use_sim_time` 和必填的 `path_map`，实机参数文件和安装 TF 仍需单独配置；在 `ros2 launch` 后追加节点级 `--ros-args` 不能代替这些参数入口。实际操作应在以下两种方式中选择一种：

1. 复制该 launch 为实机专用文件，通过 `path_map` 传入本次地图，并使用本次配置和已核实的静态变换，再构建并运行；适合后续维护。
2. 将该 launch 中已经核实的静态变换单独启动，再直接运行定位节点；适合首次逐节点诊断。

第二种方式的定位节点命令如下，**前置条件是对应 TF 已按实测完成，不能遗漏安装 TF 的先行启动和成功查询检查**。以下关闭定位节点的 `motion_link` TF，仅适用于保留旧机体链的候选诊断方案：

```bash
ros2 run open3d_loc global_localization_node --ros-args \
  --params-file "$G1_DATA/config/loc_real.yaml" \
  -p use_sim_time:=true \
  -p path_map:="$G1_DATA/maps/b300_door_01.pcd" \
  -p publish_motion_tf:=false \
  -p threshold_fitness_init:=0.5 \
  -p threshold_fitness:=0.5 \
  -r /map:=/localization/map_cloud \
  -r /scan:=/localization/scan_cloud
```

这里的 0.5 来自现有 G1 launch，只是初始实验值，不是正确定位的保证。直接运行节点时，其余未指定参数使用源码默认值，可能不同于原 launch；应保存 `ros2 param dump /global_localization_node`，后续将所需值写入专用配置，不能把两种启动方式视为完全等价。

终端 L3 运行 RViz，启用回放时间，Fixed Frame 设为 `map`，添加重映射后的地图和扫描；终端 L4 最后播放独立 B 段：

```bash
ros2 bag play "$G1_DATA/bags/loc_B_01" --clock # 仅限支持 --clock 的 rosbag2
```

B 段建议从 B300 门口标记点、演示时的朝向开始录制；这样既能验证初值，也能直接复现演示的定位过程。若沿用原组合 launch，需传入 `path_map`，完成 TF 修改并重新构建，并确认 `/rviz_map_cur` 的 `use_sim_time=true`；原 RViz 节点没有显式设置该参数。

### 7.4 定位验收

```bash
ros2 topic echo /localization_3d_confidence
```

观察后 Ctrl-C，再检查其他项：

```bash
ros2 topic echo /localization_3d_delay_ms
ros2 run tf2_ros tf2_echo map odom
```

不要同时堆大量 echo 影响负载。fitness 是配准重叠相关指标，不是“位置正确的概率”。**`/localization_3d_delay_ms` 仅是 `now - odom.header.stamp`，不是 ICP 耗时或最近成功配准年龄。** 源码在里程计回调发布缓存 fitness；即使配准线程不再成功，新里程计仍可能伴随旧 fitness。话题持续刷新不证明配准结果新鲜。

最近成功配准时间、初始化状态、连续失败次数和扫描/里程计年龄的明确健康接口及门禁仍待实现。补齐前不能仅凭上述两个话题自动使能自主运动。还需要：

- 当前扫描与地图中的墙、门、拐角是否实际对齐，是否误配到相似房间。
- B300 门口的门框、墙角、消防设施或标识牌是否对齐；把扫描叠到地图上，确认没有整体平移或旋转。
- 静止时位置和方向是否稳定，运动中是否跳变，输出是否持续新鲜。
- 已知检查点处的误差、重复运行差异及全程时延。
- 不同起点、朝向和局部遮挡下是否仍能初始化；失败后如何恢复。

同 A 包回放可以帮助回归和排查实现，但独立 B 包才开始检验泛化；两者都不能替代真机实时检查。

### 7.5 切换实时定位与失败恢复

停止播放器和所有离线节点，启动实时驱动、FAST-LIO 与定位，统一使用 `use_sim_time=false`，保留相同地图和核对过的配置。机器人先保持静止，定位通过检查后再遥控移动。

实时定位通过后，在 B300 门口按演示流程彩排一遍：把机器人放回地面标记点，启动 → 加载地图 → 初始化 → 在 RViz 中确认位置正确 → 给一个走廊目标并观察（自主速度使能前，只做规划或由遥控配合）。彩排时按第 0.2 节落实保护方案和遥控接管。演示当天不重新建图；若窗帘、灯光、门或家具状态与建图时不同，先判断影响，再决定是否使用最近一次地图。

**本章通过条件：** 独立数据和实时路线的叠合、误差、稳定性与时延满足事先约定的要求；从异常中恢复的步骤可重复。未通过时不使能导航。

定位异常时，先停用自主速度并由现场人员接管。保留异常数据，查输入、TF、地图和初值；修正后从可辨认的位置重新初始化。重启 FAST-LIO 会改变局部里程计原点，因此要重新建立地图关系，不能继续沿用旧的 `map → odom`。

## 8. 让定位与地图满足导航接口

本章开始进入**待适配/待实现**部分。Nav2 的部署需要机器人模型/TF、里程计和传感器输入等配套条件，可结合 [Nav2 官方首次机器人配置指南](https://docs.nav2.org/rolling/configuration_and_development/first_time_robot_setup_guide/) 理解整体接口；链接当前为 rolling，具体参数按实际选定的 Nav2 发行版核对。

### 8.1 导航需要什么 TF

目标设计示意如下，frame 名称可调整，但含义和发布权必须明确：

```text
map → odom → base_footprint → base_link → lidar_imu → lidar
```

| 变换/数据 | 含义 | 计划发布者 | 核查重点 |
|---|---|---|---|
| `map → odom` | 将局部运动放入保存的地图 | 地图配准定位 | 校正与失败行为、时间戳 |
| `odom → base_footprint` | 连续的平面机体运动 | 真机里程计适配器 | 不能直接使用会全局跳变的定位差分 |
| `base_footprint → base_link` | 地面投影到机体 | 机体姿态/投影适配 | 起伏、横滚俯仰、机体原点 |
| 机体到传感器 | 固定安装关系 | URDF/静态 TF | 实测旋转和平移、不重复发布 |
| `/odom` | 局部位姿与速度 | 同一里程计适配器 | frame、速度表达坐标、时间与协方差 |

每个子 frame 只有一个父 frame；每条动态变换只有一个负责发布的节点。若用 `open3d_loc` 提供 `map → odom`，不要再同时让 AMCL 发布同一变换。

`camera_init/body` 可以保留为内部 frame，但必须计算清楚到导航机体的完整变换。当前仿真 `g1_nav_tf.py` 使用 0.793 m 高度和仿真骨盆语义；将其数字改为雷达高度，无法自动解决旋转、原点偏置和步行起伏，不能直接当作真机适配完成。

### 8.2 检查二维导航地图

第 6.4 节已生成：

```text
b300_door_01/
  map.ply       三维地图
  map.pgm       二维图像
  map.yaml      图像、分辨率、原点等
  metadata.json 导出参数与统计
```

当前脚本用点云 z 的第 5 百分位估计地面，将地面以上 0.2～1.8 m 的点作为障碍，并对地面覆盖和障碍区域做膨胀。它不是通用地面分割算法，也不是完整可通行性分析。

脚本默认还补全原点附近 1.5 m 空闲区域；本文首次导出显式设为 `--known-free-radius 0`。即便关闭此项，地面覆盖膨胀也仍会扩展空闲区域，需要检查门口、墙角和未观测区。

验收时对照三维地图和实物检查：B300 门口的门宽与走廊通道、地图朝向、未知区、桌椅、低矮障碍和实际起点。`map.yaml` 的 origin 是图像角点在地图中的坐标，不是机器人初始位置；图像上下方向也不能凭肉眼直接当作地图 y 轴。

三维与二维地图必须共享已知的坐标关系。当前导出元数据假设 `map_from_camera_init` 为单位变换；若后续旋转、裁剪或平移三维地图，必须同步处理定位地图和二维地图关系。

### 8.3 实时障碍点云不是换一个话题就够了

现有 Nav2 仿真配置订阅 `/livox/lidar` 的 PointCloud2，真机候选驱动输出 CustomMsg。可以设计 CustomMsg 转换节点，也可以评估 FAST-LIO 的体坐标扫描作为输入，但两者都需要验证：

- frame 与时间戳可转换到代价地图；传感器原点正确。
- 已去除机器人自身点云，地面过滤不把地面当作障碍。
- 标记障碍与射线清除符合实际观测范围，移动障碍离开后会被合理清除。
- 降采样与盲区没有漏掉目标障碍；不能把历史累计地图冒充实时扫描。
- 步行起伏时障碍高度仍以正确的地面基准判断。

只有确认 PointCloud2 的数值语义后，才能把 `/cloud_registered_body_1` 接入障碍层。LIO 停止更新时该输入也可能失效，导航门禁应考虑此类关联失效。

**本章通过条件：** 完整 TF 可查、无重复发布；地图与机体对齐；里程计连续；静态和移动障碍在代价地图中表现合理。此时仍可以让速度桥保持禁用，仅检查感知和规划。

## 9. 将导航速度连接到 G1 运控

### 9.1 接口与职责

Nav2 输出期望平面速度，通常包括前后、横向和偏航速度。速度桥负责格式转换、控制权、时效和限幅；宇树运控负责执行。使用官方高层运控不要求本仓库的仿真 RL 控制器接管真机关节。

按原稿 EDU 型号准备高层运控路线；具体 PC2 配置、二次开发权限和设备身份待第 0 章现场复核。本地 SDK 候选接口是 `unitree::robot::g1::LocoClient::SetVelocity`，示例位于 `.deps/src/unitree_sdk2/example/g1/high_level/`。官方代码见 [G1 LocoClient](https://github.com/unitreerobotics/unitree_sdk2/blob/main/include/unitree/robot/g1/loco/g1_loco_client.hpp)，现场仍必须核对固件和固定 SDK 提交的实际支持情况，不能把“教育版”当作所有方法都可用的保证。

本地头文件中 `StopMove()` 调用零速度；它是软件运动停止请求，不等同于硬件急停。SDK 返回成功也不证明机体实际完成动作，需要状态反馈与现场观察。

停止测试按第 0.2 节逐项区分取消目标、零速、遥控接管、失能及该设备实际配备的硬件停止手段。减速和支撑状态取决于具体模式与固件，需按厂家规程和现场保护方案验证，不能从 SDK 零速调用推断必然失去支撑或实际已经停止。

### 9.2 待实现的速度桥契约

| 项目 | 应明确的行为 |
|---|---|
| 输入 | 明确最终速度话题及 Twist/TwistStamped 类型，记录控制器、平滑器和桥之间的重映射 |
| 使能 | 启动默认禁用；定位、传感器和控制状态合格后才允许自主速度 |
| 限制 | 速度与加速度约束一致，拒绝非有限值，按现场验证限制横移和转向 |
| 时效 | 以本机接收时刻检查新鲜度；对消息自带时间戳另做合理性检查 |
| 定位健康（待实现） | 检查最近成功配准年龄、初始化状态、连续失败次数，以及扫描/里程计年龄；禁止用缓存 fitness 和里程计 delay 代替配准健康 |
| 设备命令 | 固定 SDK 网卡、域、速度单位和有效期；检查每次请求结果 |
| 异常 | 输入超时、定位失效、接管、关闭使能后停止自主输出并按约定停止 |
| 断链 | 核实机器人端命令过期行为；PC2 自身 watchdog 无法在断网后送达停止请求 |
| 退出 | 正常退出请求停止；崩溃/断电情况依赖经验证的机器人端过期机制 |
| 接管 | 遥控器优先级和退出自主模式方式必须经现场验证 |
| 记录 | 输入速度、实际发送值、使能原因、SDK 返回值和机体反馈 |

可沿用仿真的 `/cmd_vel_nav` 和 `/g1/nav_enable` 命名，但接口同名不代表现有 IPC 桥已经能控制真机。

### 9.3 分阶段验证桥

先用假接收端验证门禁、限幅和超时，不接运动。随后在现场按机器人规定的测试条件单独验证高层控制、停止、接管和有限命令有效期，再与 Nav2 连接。第一次让机器人真实移动时，选择开阔平坦的地面，按第 0.2 节确认人员、保护装置和停止负责人的位置。

断链、进程退出、定位丢失和取消目标应分别验证并保留状态记录。不要直接照搬 SDK 的任意动作示例；示例可能附带模式切换或持续运动行为。

**本章通过条件：** 速度桥有实现、配置、状态反馈和现场测试记录；每条停止路径实际有效。本文当前没有可启动的真机桥，因此没有“运行某个脚本即可完成本章”的命令。

## 10. 完整真机导航部署与验收

### 10.1 创建真机独立入口

现有 `start_g1_navigation.sh` 检查仿真进程，`g1_navigation.launch.py` 及参数文件含仿真时间配置。真机应新增独立入口，保留现有仿真默认值，集中提供：

- 实机地图路径、定位配置、传感器配置和安装 TF。
- 所有相关节点的 `use_sim_time=false`，不依赖仿真 `/clock`。
- Nav2 的真机参数、生命周期管理和速度话题重映射。
- 第 9 章速度桥的网卡、域、限幅、时效和默认禁用门禁。
- 各阶段独立启动和退出，避免定位尚未初始化就自动运动。

建议将入口命名为独立的 real/real_robot 文件，但这只是命名建议，当前仓库不存在对应的已验收程序。

### 10.2 配置不能只看最大速度

| 配置项 | 真机需要核查 |
|---|---|
| footprint 与膨胀 | 躯干、腿摆动、手臂和附加设备占用范围及通行余量 |
| controller 约束 | 可执行的前进、横移、转向与加减速，不假设与仿真策略一致 |
| velocity smoother | 与 controller、速度桥约束一致，检查是否使用里程计反馈 |
| 目标容差 | 定位噪声、可控停车精度和最终朝向要求 |
| 障碍层 | 高度基准、盲区、标记/清除、传感器新鲜度 |
| 恢复行为 | 原地转向、倒退等动作是否适合现场条件，未经验证先禁用对应行为 |
| 生命周期 | 节点 active 之外，还要有地图、TF、有效输入和正确控制门禁 |

原仿真 DWB 的限速不代表平滑器和最终桥都具有同一上限，应沿实际输出链逐项核查。

### 10.3 首次完整启动顺序

每步通过后再进入下一步，所有终端使用同一实机配置。

1. 现场人员确认机体状态、遥控接管与停止手段，按第 0.2 节落实保护方案，明确停止负责人，启动传感器。
2. 先启动第 7 章要求的安装 TF，确认可查询；再启动 FAST-LIO 和地图定位，保持自主速度禁用，检查定位节点实际查询结果，完成第 7 章检查。
3. 启动其余真机 TF/里程计适配和障碍处理，避免重复发布已启动的安装 TF，完成第 8 章检查。
4. 启动地图服务器与 Nav2，确认生命周期、栅格和代价地图。
5. 在速度桥仍禁用时请求规划，检查起终点、通道和路径。此阶段只评价规划，不把因禁用执行产生的导航超时当作运动失败。
6. 确认速度桥与现场控制状态，按已经验收的方式使能，先给开阔区域的短距离目标；现场保护保持有效，直到本次测试结束。
7. 观察实际轨迹、避障、到点与停止，再测试取消目标。取消目标和各类停止测试均执行同一现场保护方案。
8. 逐步增加距离、重复路线与动态障碍；每次都记录结果。

应事先约定记录项与通过要求：实际终点误差、姿态误差、最小通行余量、定位/感知时延、停止反应及重复次数。目标 Action 成功、RViz 图标到点和现场机体实际到达，要分别核对。

### 10.4 收尾与重新启动

先取消目标并禁用自主控制，确认机体已停止，再停止 Nav2 和速度桥，最后停止定位与传感器。建图任务需要在停止 FAST-LIO 前保存并核验地图。

重新启动里程计、切换地图或移动机器人后，重新检查定位关系与门禁；不沿用前一轮“已定位”的状态。只有该流程完成并记录实测结果，才可将本文状态改为相应范围的“真机已验证”。

### 10.5 演示当天流程（B300 门口）

演示当天只加载提前建好的地图，不现场重新扫图。

1. 提前到场，按第 6.1 节的记录检查：窗帘拉上、灯打开、门的状态一致、走廊杂物已清走、地面干燥无线缆。
2. 把机器人放回地面标记点，朝向按记录摆正；确认没有偏离标记太多，否则重新记录初值。
3. 在 PC2 先启动已核实的安装 TF 和驱动，再启动 FAST-LIO、定位；检查定位节点 TF 查询成功，确认加载的是 `b300_door_01` 地图，RViz 中位置正确。
4. 启动其余 TF/里程计适配、障碍处理和 Nav2，避免重复 TF；速度桥保持禁用，先确认规划和代价地图正常。
5. 按第 0.2 节落实现场保护，停止负责人就位，遥控器由接管人持有；围观人员留在划定区域，不进入行进通道，避免持续遮挡关键定位结构。
6. 先用短距离目标试走，确认方向、避障和到点正常，再按演示路线正式执行。
7. 出现定位跳变、机器人犹豫、偏离路线或前方有人闯入时，立即禁用自主速度，由现场人员按保护方案实施遥控接管；不要在演示现场重新建图或大改参数。
8. 结束后按第 10.4 节顺序收尾，记录实际终点、停止方式和现场异常。

远程人员如需查看日志，用 SSH 连 PC2；现场不要同时用多台电脑启动节点或发布控制命令，避免出现第二个驱动、重复 TF 或两路速度。

如果现场条件与建图时差异明显，正确做法是暂停演示并回到第 6 章重新建图、第 7 章重新验证，而不是在门口临时重扫。

## 11. 排错、恢复与日常运行

### 11.1 按现象定位问题

| 现象 | 先采取的动作 | 重点证据与检查顺序 | 恢复位置 |
|---|---|---|---|
| 无点云/IMU | 保持自主控制禁用 | 驱动日志 → 接收地址/端口 → 抓包 → ROS 类型/QoS/overlay | 第 5 章静止检查 |
| 频率低或数据间断 | 停止扩大采集路线 | 发布设置 → 时间间隙 → PC2 CPU/内存/磁盘 → 温度与降频 → 驱动/网络 | 第 5 章短录包 |
| 地图重影或尺度异常 | 不继续生成导航地图 | 单位/时间 → 外参 → 畸变与退化 → 处理积压 | 第 6 章离线建图 |
| 保存返回成功但文件不可读 | 保持建图节点运行 | 目录/权限/磁盘 → 点云内容 → 写入与读回 | 第 6.4 节 |
| 定位跳变或误配 | 禁用自主速度并接管 | 输入新鲜度 → 地图版本 → 初值/坐标 → 叠合与 fitness | 第 7 章重新初始化 |
| TF 超时或 RViz 空白 | 不继续使能控制 | 回放/实时时钟 → frame 名 → 时间戳 → 发布者与 TF 连通 | 对应建图或定位检查 |
| 机器人超出代价地图 | 停止导航执行 | 地图坐标定位是否发散 → map/odom → 地图 origin/范围 | 第 7～8 章 |
| 能规划但不走 | 保持受控状态，不盲目切模式 | 门禁 → 最终速度 → 桥日志 → SDK 状态 → 现场运控模式 | 第 9 章桥验证 |
| 障碍不清除 | 暂停自主行走 | 实时扫描与传感器原点 → raytrace → 时间/高度/盲区 | 第 8.3 节 |
| 停止请求未生效 | 现场按已验证方式接管/停止 | 独立保留指令、返回值和机体反馈，不重复发试探性动作 | 第 9 章停止路径验证 |
| 停止时出现失稳 | 按已确认保护方案处理，停止测试 | 实际停止模式与支撑状态 → 速度与减速度 → 地面 → 保护记录 | 第 0.2 节与第 9 章 |
| PC2 过热、降频或明显卡顿 | 暂停采集，不再增加节点 | `top` → 内存/磁盘 → 温度与风扇 → 是否同时开 RViz 和录包 | 第 6.6 节负载检查 |
| 现场定位差、建图与演示条件不同 | 不现场重扫，先比对条件 | 窗帘/灯光/门/家具 → 场景几何变化 → 地图版本 | 第 6.1 节复现条件 |

“机器人超出地图”时先看定位，不先重启 Nav2；地图尺寸扩大也不能修复已经发散的位置估计。

### 11.2 每次实验最少保存什么

- 设备、固件、代码提交与未提交修改；驱动来源及消息版本。
- 本次控制主机是哪一台（PC2/服务器/Ubuntu 笔记本），外部电脑用什么方式接入（SSH/远程桌面/跨主机 ROS）。
- 网络方式、IP/网卡、ROS 域、RMW、各节点参数和启动命令。
- A/B 原始包、地图文件、栅格元数据和检查点记录。
- 输入质量、定位误差/时延、导航目标、结果及实际停止情况。
- 建图与演示时的窗帘、灯光、门和家具状态，以及机器人地面标记点。
- 保护与各类停止操作的分工、现场人员位置、异常发生时间和恢复步骤。

录包和参数目录使用新的编号；原始包保留不改。参数调整一次只改变可解释的内容，记录前后对照，避免同时调整时间、外参和滤波后无法判断原因。

## 附录 A：PC2 单机部署与可视化

PC2 是本次默认算力：Livox 驱动、FAST-LIO、定位、TF/障碍处理和 Nav2 都跑在它上面。先核实系统和架构：

```bash
uname -m
cat /etc/os-release
printenv ROS_DISTRO
nproc
free -h
df -h
```

- **备选 x86_64：** 按[通用部署笔记](g1_real_robot_slam_notes.md)第 4 章核对系统与动态库；同架构不保证二进制兼容。
- **本机 ARM64：** 已用 Foxy 与 ARM64 库构建驱动和 FAST-LIO。Open3D、定位和 Nav2 按实际发行版与 ABI 单独验证。

部署要点：

1. 把驱动接收 IP 改为 PC2 实际网卡地址，确保没有其他程序争用或重配雷达。
2. 地图、配置和录包放在 PC2 本地磁盘；核对路径、动态库和磁盘余量。
3. 在机载端重复静止、运动、建图和定位检查，并测量持续负载、温度、积压和时延；不能只看节点是否能启动。
4. 启动顺序固定下来，避免演示当天忘记加载驱动 overlay 或定位配置。

代码同步建议用 git 或 rsync 只同步源码和配置，不要直接复制开发机的 `build/`、`install/` 和 `.deps` 预编译库；架构或绝对路径不同会加载错误的动态库。同步后重新构建，地图、配置和录包单独拷贝并记录校验值。

外部电脑（Mac/Windows/Ubuntu）如何完成日常控制见第 3.6 节。这里只比较可视化方案，常见有三种：

| 方式 | 适用条件 | 注意 |
|---|---|---|
| PC2 接显示器 | PC2 有显示输出，人就在机器人旁边 | 最省事；所有节点本机，可用 `ROS_LOCALHOST_ONLY=1` |
| 远程桌面（NoMachine/VNC/RDP） | PC2 不方便接屏幕 | 点云画面很吃带宽；远程画面卡顿不等于算法实时性差 |
| 4060 笔记本跑 RViz | 需要另一块屏幕看地图 | 属于跨主机 ROS，见下 |

跨主机 RViz 需要：两台机器使用同一 `ROS_DOMAIN_ID` 和兼容的 RMW，PC2 关闭 `ROS_LOCALHOST_ONLY`，防火墙放行 DDS 发现与数据传输端口，并确认笔记本能 ping 通 PC2。笔记本不需要接入雷达网段，但必须能发现 PC2 的 ROS 节点。远程桌面和跨主机 RViz 不要同时用来判断实时性，负载会互相干扰。

```text
MID-360 → PC2（驱动 + FAST-LIO + 定位 + Nav2）
                 ├─ 本机显示器 / 远程桌面
                 └─ 4060 笔记本（可选，只看 RViz）
```

机载运行减少了雷达原始数据对外部网络的依赖，但不自动解决外部控制断链或算力不足。PC2 长时间满载前要确认风扇、供电和磁盘余量；断电或重启后重新检查驱动、网络和 overlay。

### A.1 在 Ubuntu 本地查看现有录包

适合把机器人录到的数据拷到已部署本项目的 Ubuntu 电脑上检查。Ubuntu 端需能解析 `livox_ros_driver2` 和 `fast_lio`，且 CustomMsg 与录包版本兼容。回放时只启动 FAST-LIO、播放器和 RViz。

先从 Ubuntu 电脑复制整个录包目录及参数。以下目录可按本机实际路径调整：

```bash
mkdir -p "$HOME/g1_real_data/bags" "$HOME/g1_real_data/config" "$HOME/g1_real_data/records"
scp -r unitree@192.168.123.164:/home/unitree/g1_real_data/bags/static_01 "$HOME/g1_real_data/bags/"
scp unitree@192.168.123.164:/home/unitree/g1_real_data/config/mid360_real.yaml "$HOME/g1_real_data/config/"
```

Ubuntu 的三个 Bash 终端都加载本机工作区，使用同一个域：

```bash
export G1_REPO="$HOME/FAST_LIO_LOCALIZATION_HUMANOID"
export G1_DATA="$HOME/g1_real_data"
export ROS_DOMAIN_ID=193 ROS_LOCALHOST_ONLY=1
source "$G1_REPO/scripts/walking_env.sh"
```

1. 终端一启动 FAST-LIO，关闭 PCD 保存。
   ```bash
   ros2 run fast_lio fastlio_mapping --ros-args \
     --params-file "$G1_DATA/config/mid360_real.yaml" \
     -p use_sim_time:=false -p pcd_save.pcd_save_en:=false \
     -p debug_log_dir:="$G1_DATA/records"
   ```
2. 在 Ubuntu 图形桌面的终端二打开 RViz。
   ```bash
   rviz2 -d "$G1_REPO/FAST_LIO/rviz/fastlio.rviz"
   ```
   确认 **Fixed Frame = `camera_init`**，启用 **PointCloud2 → `/cloud_registered_1`**。该话题是 FAST-LIO 配准后的点云，原始 `/livox/lidar` 是 Livox 自定义类型。若要看里程计，把配置的 Odometry 话题改为 `/Odometry_loc`。
3. 终端三用 `ros2 bag info "$G1_DATA/bags/static_01"` 验证播放器能读取包，再启动回放：
   ```bash
   ros2 bag play "$G1_DATA/bags/static_01"
   ```

若窗口没有点云，先看 FAST-LIO 日志有没有完成 IMU 初始化，再用 `ros2 topic info /cloud_registered_1 --verbose` 检查发布者和 QoS。点云显示可以只保留同坐标系的 PointCloud2，便于排除历史 TF 对其他显示项的影响。PC2 Foxy 已实测录包回放，以及实时模式下的点云发布，外部 Ubuntu 的本机包兼容性及 RViz 窗口待在该电脑上核对。

实时查看时，最直接的入口是在 **PC2 的 Ubuntu 图形桌面**打开同一个 RViz 配置（可通过远程桌面操作），另用 PC2 终端按第 5.2 节启动驱动，再运行上述 FAST-LIO 命令。三个终端使用同一 PC2 域。若把 RViz 放在另一台 Ubuntu 上，按本附录前文核对 DDS 发现，并在 Ubuntu 端用 `ros2 topic info /cloud_registered_1 --verbose` 确认可见发布者后再看画面。
